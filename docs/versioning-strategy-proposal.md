# Cyoda Dev Console — Workflow Versioning Strategy

**Status:** Draft for review  
**Date:** 2026-06-16  
**Author:** Patrick Stanton  
**Context:** cyoda-dev-console wraps cyoda-workflow-editor; legacy workflows produced by older cyoda-go versions fail to load in the current console.

---

## Problem Statement

The dev console must open workflow JSON files that were generated by any cyoda-go version a developer has used — not just the current one. Right now, schema drift between cyoda-go releases causes two categories of failure:

1. **Naming inconsistencies** (e.g. `"external"` → `"externalized"` processor type) break Zod validation in `parseImportPayload`, making legacy files completely unusable.
2. **Structural changes** (field additions/removals, nesting changes) cause silent data loss or validation errors with no useful diagnostic.

The dev console must not become so tightly coupled to a single cyoda-go schema version that any new cyoda-go release forces a console upgrade.

---

## Architecture Touchpoints

The workflow passes through a well-defined pipeline that constrains where versioning logic can live:

```
Disk (cyoda-go JSON)
  ↓
parseImportPayload()          ← @cyoda/workflow-core
  ↓  JSON.parse → Zod → alias normalise → assign UUIDs → validate
WorkflowEditorDocument        ← canonical internal model
  ↓
WorkflowEditor component      ← @cyoda/workflow-react
  ↓
serializeImportPayload()      ← @cyoda/workflow-core
  ↓
Disk (clean Cyoda workflow JSON)
```

The CLAUDE.md invariant is explicit: **saved JSON must always be produced by `serializeImportPayload(document)`**. This means the inbound normalization step — inside `parseImportPayload` — is the natural and only correct place to absorb schema differences. Nothing in the dev-console or workflow-editor-host should need to know about schema versions directly.

---

## Strategy: Two-Tier Compatibility

### Tier 1 — Non-Breaking Changes: Normalisation Adapters in `workflow-core`

For schema differences that are structurally equivalent but syntactically different (renames, field aliases, additive fields), the fix belongs inside `parseImportPayload` as a pre-Zod normalisation pass.

**How it works:**

```
parseImportPayload(rawJson)
  1. Detect schema version (see "Version Detection" below)
  2. Run applicable normalizer chain  ← NEW
  3. Zod schema validation           ← existing
  4. Alias normalization             ← existing
  5. UUID assignment + semantic validation  ← existing
```

The normalizer chain is a registry of small, versioned transformer functions, applied in order:

```ts
// packages/workflow-core/src/normalizers/index.ts

type Normalizer = {
  id: string;                          // e.g. "rename-external-to-externalized"
  appliesTo: (raw: unknown) => boolean; // predicate: does this JSON need this fix?
  transform: (raw: unknown) => unknown; // pure transform, no side effects
};

const NORMALIZERS: Normalizer[] = [
  {
    id: "rename-external-to-externalized",
    appliesTo: (raw) => hasProcessorType(raw, "external"),
    transform: (raw) => renameProcessorType(raw, "external", "externalized"),
  },
  // add future normalizers here
];
```

Each normalizer is:
- **Self-describing** — the `id` is logged so developers can see which normalizations were applied.
- **Idempotent** — safe to apply to already-current JSON.
- **Predicate-gated** — only runs if its `appliesTo` check matches, so current-version files have zero overhead.

The result: any dev-console code that calls `parseImportPayload` (including the workflow-editor-host package) gets backward compatibility automatically, with no changes needed above `workflow-core`.

**Immediate fix for the `"external"` bug:** This is a Tier 1 change. Add one normalizer. Legacy workflows load.

---

### Tier 2 — Breaking Changes: Console Version Pinning

For structurally incompatible schemas — where the semantic meaning of a field has changed, a required concept has been removed, or the object graph has been reorganised — no adapter can safely bridge the gap without guessing intent.

In these cases:

- A **new major version of the dev console** is required.
- The old console version remains installable for users on older cyoda-go.
- The console advertises which cyoda-go version range it supports (see "Compatibility Matrix" below).
- If a workflow is detected as incompatible, the console shows a **clear error with an upgrade path**, not a generic parse failure.

The threshold for "breaking" should be conservative: if an adapter would need to infer the developer's intent rather than mechanically transform the JSON, it's a breaking change.

## Version Detection

Reliable version detection requires a two-pass approach:

**Pass 1 — Explicit version field**

Prefer an explicit field in the workflow JSON that cyoda-go writes:

```json
{ "meta": { "cyodaGoVersion": "1.4.2", ... }, ... }
```

If cyoda-go does not currently write this, add it. The normalizer pipeline can still run on files that lack it using Pass 2.

**Pass 2 — Structural fingerprinting**

For files produced before the version field existed, detect schema generation by structural signatures:

```ts
function detectSchemaGeneration(raw: unknown): "v1-legacy" | "v1-current" | "unknown" {
  // e.g. presence of processor.type === "external" → v1-legacy
  // presence of processor.executionMode → v1-current
}
```

Fingerprinting should be conservative: if the generation is ambiguous, default to running all applicable normalizers in order. Since normalizers are predicate-gated, safe-to-skip ones don't transform anything.

## What Goes Where

| Concern | Location | Rationale |
|---|---|---|
| Normaliser chain | `@cyoda/workflow-core` — `parseImportPayload` | Single point of entry; all consumers benefit automatically |
| Normaliser registry | `packages/workflow-core/src/normalizers/` | Co-located with the Zod schema it feeds |
| Detected version (diagnostic) | Returned in `ParseResult` | Lets the dev-console surface it in UI without needing to re-detect |
| Target cyoda-go version per project | `workflow-project-model` — `DevProject` | Project-level, not file-level; used for outbound serialization hints and AI context |
| Version badge / warning UI | `workflow-editor-host` | Integration layer between core and the Tauri app |
| Compatible version range declaration | `apps/dev-console/package.json` — `cyodaGoCompatibility` field | Machine-readable; can be checked at startup against a live environment |

## Dev-Console UX Changes

### File tree
- Each workflow entry in the file tree shows a small version badge (detected generation) when it differs from the project target.
- Files that required normalisation get a subtle "upgraded schema" indicator — not an error, just informational.

### Project settings
- "Target cyoda-go version" field in project config (stored in `workflow-project-model`).
- When set, the console validates on save that `serializeImportPayload` output is compatible with that target.

### Error states
Replace the current generic `"parse-error"` status with structured errors:

```ts
type WorkflowFileStatus =
  | "valid-workflow"
  | "valid-workflow-normalised"    // loaded OK after normalisation
  | "invalid-workflow"
  | "incompatible-version"         // Tier 2: requires different console version
  | "json-not-workflow"
  | "parse-error";
```

`incompatible-version` shows a banner: "This workflow was created with cyoda-go X.Y which is not supported by this console. Install dev-console vN or downgrade cyoda-go."

### Ops Console
When connected to a live Cyoda environment, `cyoda-api-client` should read the environment's cyoda-go version from the API and surface it:
- In the connection status bar.
- As an input to `parseImportPayload` (skip fingerprinting; use known version directly).
- As a warning if the environment version is outside the console's compatible range.

## Compatibility Matrix (proposed)

| Dev Console version | Supported cyoda-go range | Notes |
|---|---|---|
| 1.x | 1.0 – 1.x | Tier 1 adapters cover `external→externalized` and other minor renames |
| 2.x | 2.0+ | Required if structural breaking changes land in cyoda-go 2.0 |

The console should declare this in a machine-readable field:

```json
// apps/dev-console/package.json
{
  "cyodaGoCompatibility": { "min": "1.0.0", "max": "1.x" }
}
```

## Naming Consistency (Immediate Action)

The meeting called out AI confusion caused by inconsistent naming (`externalized` vs `external`). Beyond the runtime fix, the schema needs to be the single source of truth:

1. The Zod schema in `workflow-core` should be the canonical definition.
2. Any cyoda-go OpenAPI spec that disagrees with the Zod schema is a bug to fix on the cyoda-go side.
3. The normalizer documents the known historical aliases, making future discrepancies immediately visible in code review.

---

## Implementation Sequence

1. **Immediate:** Add the `rename-external-to-externalized` normalizer to `workflow-core`. Ship in next patch. Fixes legacy workflow load failures today.

2. **Short-term:** Add `ParseResult.normalisationsApplied` and `ParseResult.detectedSchemaGeneration` to the return type of `parseImportPayload`. Update `workflow-editor-host` to surface these in the file tree.

3. **Short-term:** Add `cyodaGoVersion` to the cyoda-go workflow output format. Add `targetCyodaGoVersion` to `DevProject` in `workflow-project-model`.

4. **Medium-term:** Structured `incompatible-version` error state in the file indexer. Version badge in file tree UI.

5. **Ongoing:** Any cyoda-go schema change ships with a corresponding normalizer PR in `workflow-core`. The normalizer is the migration record.

---

## What This Avoids

- **Forking the dev-console per cyoda-go minor version** — the adapter pattern means one console handles a range.
- **Silent data loss** — normalizations are explicit, logged, and auditable.
- **AI confusion from schema inconsistency** — the Zod schema becomes the authoritative source; historical aliases are named and contained.
- **Rigid coupling** — the dev-console has no direct knowledge of cyoda-go schema details; it only depends on `parseImportPayload` behaving correctly.
